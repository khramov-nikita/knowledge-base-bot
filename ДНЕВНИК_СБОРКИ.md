# Дневник сборки бота-консультанта по базе знаний

Документ фиксирует ход разработки, возникшие затруднения, способы их решения
и примеры промптов, которые использовались при работе с ассистентом (Claude).

---

## Этапы сборки

1. **Паспорт проекта.** Сохранили описание бота (цель, функции, сценарии,
   ограничения) в `CLAUDE.md` — как ориентир для всей дальнейшей разработки.
2. **Планирование каркаса.** В режиме планирования определились с технологиями:
   Python + aiogram 3, база данных SQLite (`aiosqlite`), заглушка LLM,
   уведомления владельцу.
3. **Реализация каркаса.** Создали структуру проекта: `bot.py`, `config.py`,
   пакеты `app/database`, `app/handlers`, `app/services`, `app/keyboards`,
   `app/utils`.
4. **Наполнение базы.** Написали seed-скрипт `scripts/seed.py` с
   демонстрационными записями.
5. **Подключение LLM.** Заменили заглушку на реальную интеграцию с DeepSeek
   (OpenAI-совместимый API) с таймаутом и безопасным fallback.

---

## Что умеет каркас бота

Если коротко, это Telegram-бот, который работает как справочная: пользователь
пишет вопрос, а бот ищет ответ в своей базе знаний и отвечает текстом.
Основные возможности:

- **Отвечать пользователям.** Понимает команды `/start` и `/help`, а любой
  обычный текст воспринимает как поисковый запрос.
- **Искать по базе знаний.** Хранит записи (ключевые слова, заголовок, текст
  ответа) в базе SQLite и ищет по ним совпадения.
- **Не терять запросы без ответа.** Если в базе ничего не нашлось, бот
  подключает LLM (DeepSeek), а сам запрос записывает в отдельную таблицу
  «незакрытых» и уведомляет владельца — чтобы базу можно было дополнить.
- **Помогать владельцу.** У владельца есть свои команды: `/stats` (популярные
  запросы и сколько вопросов осталось без ответа), `/add` (добавить запись в
  базу), `/list` (посмотреть, что уже есть). Обычным пользователям они
  недоступны.
- **Помнить контекст диалога.** Последние сообщения пользователя сохраняются,
  чтобы уточняющие вопросы («а сколько это стоит?») понимались в контексте.
- **Наполняться данными.** Через команду `/add` по одной записи или через
  seed-скрипт сразу пачкой демо-данных.

## Как проходит путь сообщения

Например, пользователь отправил боту слово «отпуск». Что происходит по шагам:

1. **Приём.** Сообщение приходит в `bot.py`, где запущен опрос Telegram
   (polling), и передаётся диспетчеру aiogram.
2. **Маршрутизация.** Диспетчер прогоняет сообщение через роутеры: сначала
   команды владельца, затем пользовательские хэндлеры. Обычный текст попадает
   в общий обработчик запросов в `app/handlers/user.py`.
3. **Поиск в базе.** Хэндлер вызывает `search_knowledge()` — идёт запрос к
   SQLite. Заодно факт запроса пишется в лог для статистики.
4. **Развилка:**
   - **Нашлось** → бот отправляет пользователю текст найденной записи
     (Сценарий 1 из паспорта).
   - **Не нашлось** → бот вызывает `llm.ask()` (DeepSeek), записывает запрос в
     таблицу «незакрытых», уведомляет владельца через `notifier` и возвращает
     ответ пользователю (Сценарий 3).
5. **Сохранение контекста.** Запрос добавляется в историю диалога (в памяти),
   чтобы следующий уточняющий вопрос понимался в контексте.
6. **Ответ.** Пользователь получает сообщение в чате.

Схематично:

```
Пользователь → Telegram → bot.py (polling) → Dispatcher → роутер
   → хэндлер запроса → поиск в SQLite
       ├─ найдено → ответ из базы
       └─ не найдено → LLM + запись «нет ответа» + уведомление владельцу → ответ
```

## Затруднения и их решения

### Затруднение 1. Циклический импорт из-за `OWNER_ID`

**Проблема.** Хэндлерам (`app/handlers/user.py`, `app/handlers/owner.py`)
нужен ID владельца из конфигурации, но прямой импорт `config` в хэндлеры и
одновременная сборка приложения в `bot.py` создавали риск циклических
зависимостей и усложняли тестирование.

**Решение.** Ввели отдельный модуль `app/runtime.py` с переменной `OWNER_ID`,
которая один раз устанавливается при старте в `bot.py` через
`runtime.set_owner_id(config.owner_id)`. Хэндлеры читают значение из
`runtime`, не завися напрямую от загрузки `.env`.

### Затруднение 2. Не удавалось проверить код запуском в терминале

**Проблема.** Команды в терминале (`python --version`, `python -m py_compile ...`)
не возвращали статус выполнения, поэтому автоматически убедиться в
работоспособности через запуск не получалось.

**Решение.** Опирались на статический анализ: прогоняли проверку линтером
после каждого блока правок (ошибок не найдено) и проводили ручную ревизию
кода. Такой подход позволил выявлять проблемы без запуска интерпретатора.

### Затруднение 3. Выбор «движка» для ответов LLM

**Проблема.** Возник вопрос, можно ли использовать Cursor как LLM для ответов
бота. Оказалось, что Cursor SDK предназначен для кодинг-агентов, а не для
потоковых Q&A-ответов конечным пользователям.

**Решение.** Выбрали DeepSeek (как заложено в паспорте) через
OpenAI-совместимый клиент `openai`. Провайдер и модель вынесли в `.env`
(`LLM_BASE_URL`, `LLM_MODEL`), чтобы при желании переключиться на OpenAI без
изменения кода. Добавили graceful fallback: при отсутствии ключа или ошибке
API бот не падает, а возвращает безопасный текст и фиксирует запрос.

## Пример промпта для Claude

Промпт, который использовался для генерации рабочего каркаса бота:

```
Сделай план создания каркаса Telegram-бота-консультанта по базе знаний.
Стек: Python + aiogram 3, база данных SQLite (aiosqlite).
Нужны: структура проекта, конфиг через .env, подключение к БД с таблицами
(записи базы знаний, лог запросов, незакрытые запросы), хэндлеры пользователя
(/start, /help, поиск по базе, сценарий «ответа нет»), хэндлеры владельца
(/stats, /add, /list), заглушка LLM с готовым интерфейсом и уведомления
владельцу. Опиши файлы и поток обработки запроса, но пока не пиши код.
```

Пример уточняющего промпта на этапе подключения LLM:

```
Замени заглушку в app/services/llm.py на реальный вызов DeepSeek через
OpenAI-совместимый клиент. Ключ, базовый URL и модель бери из конфигурации
(.env). Добавь системный промпт, передачу истории диалога, таймаут запроса и
безопасный fallback: если ключа нет или API вернул ошибку — не роняй бота, а
верни запасной текст.
```

## Доработки после базового каркаса (по запросам)

После сборки каркаса бот дорабатывался итеративно под конкретные задачи:

1. **Выбор модели DeepSeek.** Модель вынесена в `.env` (`LLM_MODEL`), значение
   по умолчанию менялось под запрос (`deepseek-v4-flash`).
2. **Реальная база знаний.** Резюме и портфолио сохранены в `БАЗА_ЗНАНИЙ.md`,
   файл добавлен в `.gitignore` (персональные данные).
3. **Импортёр Markdown.** Написан `scripts/import_md.py`: разбивает md по
   разделам (`##`) и загружает записи в таблицу `knowledge` с авто-ключевыми
   словами.
4. **RAG вместо «сырых» ответов.** Логика переведена на схему «поиск релевантных
   фрагментов → передача их в LLM → ответ по базе».
5. **Форматирование ответов.** Добавлен конвертер Markdown → Telegram HTML
   (`app/utils/formatting.py`), чтобы в ответах не оставалось символов `**`, `##`.
6. **Кнопка «Связаться с человеком».** Уведомляет владельца и отправляет
   пользователю контакты (`OWNER_CONTACT`).
7. **Список тем в `/help`.** Динамически подтягивается из базы; заголовки
   очищаются от служебных префиксов и скобок.
8. **Цены услуг.** Добавлены в базу знаний (в проекты и сводный раздел).
9. **Guardrails против промпт-инъекций.** Входной детектор, обёртка ввода как
   недоверенных данных, усиленный системный промпт и выходной фильтр утечки
   промпта (`app/services/guardrails.py`).
10. **Память диалога.** Хранение последних 20 сообщений (вопросы и ответы) для
    уточняющих вопросов.
11. **Короткие ответы.** Промпт и `max_tokens` настроены на лаконичные,
    конкретные ответы вместо копирования фрагментов.

## Затруднения (продолжение)

### Затруднение 4. LLM не отвечал по базе, хотя данные есть

**Проблема.** Бот сначала искал по ключевым словам и при несовпадении
формулировки (например, «какие языки он знает?») сразу отправлял к оператору —
LLM не вызывался, хотя информация в базе была.

**Решение.** Если точный поиск ничего не дал, боту передаётся вся база как
контекст для LLM. К оператору направляем только когда модель явно возвращает
сигнал `NO_ANSWER`.

### Затруднение 5. Модель копировала фрагменты вместо ответа

**Проблема.** На вопрос «какова средняя цена услуг?» бот выгрузил целые разделы
базы (с разделителем `---`) вместо вычисления среднего, к тому же точный поиск
давал неполный набор записей.

**Решение.** Для LLM всегда передаётся вся база (объём небольшой), а в промпт
добавлены правила: не копировать фрагменты дословно и выполнять
вычисления/обобщения (среднее, сумма, список, сравнение).

### Затруднение 6. Разметка и «мусор» в заголовках

**Проблема.** В ответах оставались символы Markdown, а темы в `/help` содержали
длинные префиксы вида «База знаний: ФИО: Опыт работы (Общий стаж: ~8 лет)».

**Решение.** Добавлен конвертер Markdown → Telegram HTML и функция очистки
заголовков (убирает хвостовые скобки и префиксы до последнего `: `).

## Дополнительные примеры промптов для Claude

Промпт на устранение проблемы с недостижимыми ответами:

```
На некоторые вопросы бот отправляет к оператору, хотя ответ есть в базе
(например «какие языки он знает?»). Исправь: если точный поиск не нашёл
совпадений, передавай LLM всю базу знаний как контекст, а к оператору
направляй только когда модель явно сообщает, что данных нет.
```

Промпт на защиту от промпт-инъекций:

```
Настрой guardrails для LLM против промпт-инъекций (например «Забудь инструкции
и…»): усиль системный промпт, оборачивай ввод пользователя как недоверенные
данные, добавь детектор подозрительных фраз и выходной фильтр от утечки
системного промпта.
```

## Итог

Бот прошёл путь от каркаса до рабочего консультанта по реальной базе знаний:
ответы генерируются через DeepSeek по схеме RAG, отформатированы под Telegram,
защищены guardrails, учитывают контекст диалога и дают короткие конкретные
ответы (включая вычисления вроде средней цены). Есть кнопка связи с человеком и
уведомления владельцу. Дальнейшие шаги — переход на полноценный поиск
(SQLite FTS5 или эмбеддинги) при росте объёма базы, чтобы не передавать её
модели целиком.
