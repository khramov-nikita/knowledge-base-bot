# Паспорт бота и правила проекта

Документ для ассистента и разработчика: что делает бот, как устроен код,
как запускать и что нельзя коммитить.

---

## Название бота

Бот-консультант по базе знаний (или «БазаЗнанийBot»)

---

## Цель и задачи

**Цель:**  
Обеспечить пользователям быстрый и круглосуточный доступ к информации из
структурированной базы знаний и каталогу услуг без участия человека.

**Задачи:**
- Отвечать на запросы по базе (RAG + DeepSeek).
- Показывать витрину услуг, хранить корзину между сессиями, оформлять заказ
  и принимать оплату через ЮKassa (тестовый режим).
- Снижать нагрузку на ответы на однотипные вопросы.
- Фиксировать запросы без ответа и уведомлять владельца.
- Хранить контекст диалога (включая действия по кнопкам) в SQLite после
  перезапуска бота.

---

## Целевая аудитория

Клиенты и потенциальные заказчики (справка об исполнителе и услугах: портфолио,
цены) и владелец, управляющий содержимым базы.

---

## Функции для пользователя

1. **Поиск / RAG** — свободный текст; релевантные фрагменты SQLite → LLM;
   короткий ответ. Меню не перехватывает обычные вопросы.
2. **Витрина** — карточки услуг (название, описание, цена) с кнопкой
   «Добавить в корзину»; короткое подтверждение после добавления;
   повторное добавление той же услуги — «Уже в корзине» (без дубля).
3. **Корзина** — список позиций с ценами и итоговой суммой; под сообщением
   кнопки «Убрать» у каждой позиции и «Оформить заказ». Корзина в SQLite
   между сессиями (`UNIQUE(user_id, service_id)`). Пустая корзина —
   вежливое сообщение и подсказка открыть «Витрина».
4. **Оформление заказа** — из содержимого корзины создаётся заказ со статусом
   «ожидает оплаты» (`orders` + `order_items`); корзина очищается; клиент
   видит состав, сумму и кнопку «Оплатить» (если сумму удалось распознать).
5. **Оплата (ЮKassa)** — «Оплатить» создаёт платёж на сумму заказа из БД и
   присылает ссылку + кнопку «Я оплатил»; повторный «Оплатить» переиспользует
   активный платёж. «Я оплатил» проверяет статус в ЮKassa: при успехе статус
   заказа → «оплачен», клиенту — благодарность; иначе — просьба завершить
   оплату. Уже оплаченный заказ повторно не меняется.
6. **Меню и связь с человеком** — «Витрина», «Корзина», «Связаться с человеком»;
   контакты из `OWNER_CONTACT`; уведомление владельцу (не себе).
7. **Нет ответа** — сообщение пользователю + запись в `unanswered` + уведомление.
8. **Память диалога** — до 20 последних сообщений в SQLite (в т.ч. действия
   кнопок); передаются в LLM при каждом запросе.

---

## Функции для владельца

1. Уведомления о незакрытых запросах, о «Связаться с человеком» и о новом
   оплаченном заказе (не себе).
2. `/stats` — популярные запросы и число незакрытых.
3. `/add`, `/list` — управление записями базы знаний.

---

## Сценарии использования

1. **Вопрос** → поиск фрагментов → LLM (+ история) → короткий ответ.
2. **Уточнение** («а цена?», «что в корзине?») → история из SQLite → ответ
   в контексте. `/start` историю и корзину не сбрасывает.
3. **Нет данных** → сообщение + уведомление владельцу.
4. **Витрина** → карточки из базы → «Добавить в корзину» → запись в
   `cart_items` + короткое подтверждение.
5. **Корзина** → список, цены, итог; «Убрать» удаляет позицию из БД и
   обновляет сообщение (сумма пересчитывается); пустая — подсказка про витрину.
6. **Оформить заказ** → атомарно: заказ (`ожидает оплаты`) + позиции + очистка
   корзины → клиенту состав, сумма и «Оплатить». Пустая корзина / повторный
   клик — заказ не создаётся.
7. **Оплатить** → платёж в ЮKassa (описание `Заказ №{id}`, сумма из позиций) →
   ссылка + «Я оплатил» → при `succeeded` статус `оплачен` + notify владельцу.
8. **Связаться с человеком** → контакты пользователю; уведомление владельцу.

## Стек и интеграции

| Компонент | Назначение |
|---|---|
| Python 3.11+, aiogram 3 | Telegram-бот (polling) |
| SQLite + aiosqlite | База знаний, пользователи, корзина, заказы, диалог |
| DeepSeek (`deepseek-v4-flash`) | RAG-ответы (OpenAI-совместимый API) |
| ЮKassa (`yookassa` SDK) | Создание и проверка платежей (тестовые ключи) |
| python-dotenv | Конфиг из `.env` |

### Таблицы SQLite (`DB_PATH`, обычно `data/knowledge.db`)

- `knowledge` — база знаний  
- `users` — пользователи Telegram  
- `cart_items` — корзина (`UNIQUE(user_id, service_id)` — без дублей услуги)  
- `dialog_messages` — история диалога  
- `orders` / `order_items` — заказы (статус «ожидает оплаты» / «оплачен»,
  `payment_id` ЮKassa) и позиции  
- `query_log` / `unanswered` — статистика и незакрытые вопросы  

Секреты в БД **не** хранятся — только в `.env`.

## Запуск

```bash
pip install -r requirements.txt
cp .env.example .env   # заполнить BOT_TOKEN, OWNER_ID, OWNER_CONTACT, LLM_API_KEY, YOOKASSA_*
python -m scripts.import_md --reset   # или scripts.seed
python bot.py                         # только один процесс!
```

Переменные `.env`: `BOT_TOKEN`, `OWNER_ID`, `OWNER_CONTACT`, `DB_PATH`,
`LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL`, `YOOKASSA_SHOP_ID`,
`YOOKASSA_SECRET_KEY`.

Тестовый режим ЮKassa = тестовые ключи (секрет обычно начинается с `test_`).
Ключи должны быть полными, без символа `*`.

## Архитектурные правила (для правок кода)

1. **Один ответ на сообщение** — кнопки меню и RAG обрабатываются в едином
   `dispatch_text`; не дублировать хэндлеры на один и тот же `F.text`.
2. **В LLM — не вся БД**, а релевантные фрагменты (`select_context_for_query` +
   `_compact_knowledge` с отбором строк по запросу).
3. **История диалога в SQLite**, не только в MemoryStorage FSM — иначе пропадает
   после рестарта.
4. **Markdown ответов** конвертировать через `md_to_telegram_html` перед отправкой.
5. **Guardrails** не ослаблять без необходимости: системный промпт, обёртка ввода,
   выходной фильтр.
6. При `NO_ANSWER` от модели, если фрагменты базы есть — отвечать по ним, а не
   сразу «данных нет».
7. Уведомления владельцу («Связаться с человеком», оплаченный заказ) не слать,
   если действие совершил сам владелец.
8. **Корзина / заказ** — callbacks `cart:add:`, `cart:remove:` (id строки
   `cart_items`), `cart:checkout`; оформление только через `checkout_cart`
   (одна транзакция). Повторное «Убрать» и checkout пустой корзины — без ошибок
   и без лишних заказов.
9. **Оплата** — callbacks `pay:create:{order_id}`, `pay:check:{order_id}`;
   сумма только из позиций заказа в БД; `payment_id` хранить в `orders`;
   активный платёж не дублировать; статус `оплачен` ставить атомарно
   (`only_if_status="ожидает оплаты"`), чтобы не слать повторный notify;
   ключи ЮKassa — только из `.env`, в коде не хардкодить. Webhook не используем —
   статус проверяется по кнопке «Я оплатил».

## Ограничения и риски

**Ограничения:** только текст и кнопки; факты зависят от полноты базы; оплата
через ЮKassa без webhook (подтверждение по кнопке); чеки 54-ФЗ не формируются;
количество позиции в корзине всегда 1; если `price_text` не парсится — кнопка
«Оплатить» не показывается.

**Риски:** недоступность БД/сервера/ЮKassa; неверный секретный ключ; неточный
ответ LLM; утечка токена/ключей; персональные данные в SQLite — файл не коммитить.

---

## Не коммитить

- `.env`  
- `*.db` / `data/*.db`  
- `БАЗА_ЗНАНИЙ.md` (персональные данные)  
- `ДНЕВНИК_СБОРКИ.md`  
- `ОТВЕТ_ДЗ.md` и `*ДЗ*.md`  

Шаблоны без секретов: `.env.example`, `README.md`.
